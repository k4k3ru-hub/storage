# ニュース収集間隔のDB管理設計

2026-11-01、ユーザーレビュー承認後に保存APIとMarketHubの単発コマンドを実装した。
承認済み[追加DDL](collection-schedule.proposed.sql)は1テーブルで、実装用の
[追加DDL](collection-schedule.sql)・`ScheduleSchema()`・MarketHubの004 migrationと本文が一致する。
既存の[DDL](schema.sql)・[当初のレビュー済みDDL](schema.proposed.sql)・`Schema()`は保持する。
今回のschedule追加分の公開・正式な依存固定、本番DB適用・実収集・定期起動登録は未実施。
保存APIは[README](README.md#収集間隔の保存契約)、MarketHubのコマンドと検証・導入順序は
[本体の仕様](../../../../k4k3ru/docs/internal/ASSET_CONTENT.md#source-collection-schedules-2026-11-01)を参照。

## 分担と初期設定

設定単位はAssetやカテゴリではなく、取得口を表す `source_id` とする。
一つのフィードから複数Assetの記事を得てもHTTP取得は1回で、その後に分類する。
storageは汎用の設定保存・検証・履歴参照を提供し、HTTP取得や定期起動を行わない。
MarketHubが承認済みの情報源を収集・分類し、取得スキルはAPIの保存済みデータをmanifestに固定する。

| MarketHubの情報源 | 承認済み間隔 | 導入時 |
| --- | ---: | --- |
| `sui-blog` | 3,600秒（1時間） | 自動収集無効で登録し、動作確認後に有効化 |
| `sui-status` | 900秒（15分） | 同上 |

この初期値はMarketHub側の設定であり、storageの既定値・seedには含めない。
導入後は本番のsystemd timer等が1分ごとに単発コマンド `markethub news collect-due` を起動する想定で、
定期起動の登録は別途運用者が行う。
ジョブは対象を確認し、各情報源を最大1回収集して終了する。プロセス内で待ち続ける処理、
Mac側の常駐サービス、未実行回数分の追いつき取得は追加しない。

## 追加テーブル

汎用名は `news_source_schedules`、K4K3RUでは `market_hub_news_source_schedules`。
ソース登録の `registration_version` と独立させ、間隔変更で取得URL・解析器の承認を変更しない。

| 列 | 意味・制約 |
| --- | --- |
| `source_id` | 既存 `news_sources` へのFK・主キー。1ソース1行 |
| `auto_fetch_enabled` | 自動起動だけの有効状態。初期false。`news_sources.enabled` は手動を含む取得可否を制御 |
| `interval_seconds` | 承認範囲は60〜604,800秒（1分〜7日）。0を無効化の意味に使わない |
| `settings_version` | 初回1、間隔・自動起動設定の変更ごとに+1。期待する版と一致する場合だけ更新 |
| `retry_not_before_at` | 配信元の `Retry-After` による待機期限。未指定NULL。再起動後も守るため保存 |
| `created_at` / `updated_at` | UTC、マイクロ秒。`updated_at` は待機期限の変更でも更新 |

設定更新APIは間隔・自動起動だけを受け付け、待機期限を上書きしない。待機期限の延長は
行ロック下で既存値と新値の大きい方を保存し、設定の版は進めない。期限が過ぎても値は保持してよい。
`settings_version` は同時編集の取りこぼし防止であり、過去の設定を再現する履歴テーブルではない。
運用記録には情報源、run ID、適用した設定の版・間隔、実行／見送り理由を残す。

実行履歴・最終成功時刻・実行中状態は既存 `news_fetch_runs` を正本にする。
次回時刻や失敗回数を重複保存する列は追加しない。初期規模では設定行を順に評価し、既存の
`ix_news_fetch_attempt` でソースごとの直近3試行を読む。大量ソース向けのdue時刻索引は別途検討する。

## 実行時刻の判定

自動対象は、ソース有効・承認済み登録と一致・スケジュールあり・自動収集有効のすべてを満たすもの。
同じソースの `running` があれば、時刻にかかわらず新規取得しない。
判定はUTCで行い、直近試行の順序は既存索引と同じ `started_at DESC, run_id DESC` とする。
整合しない終了時刻・未来の取得履歴は自動補正せず、そのソースを見送って報告する。

```text
I = 現在設定されている interval_seconds
n = 直近の連続した取得失敗数（計算には最大3件を使う）
delay = max(I, min(I × 2^n, 86,400秒))
due_at = 最新試行の finished_at + delay
実行可能時刻 = max(due_at, retry_not_before_at)
```

最新試行が成功ならn=0。履歴がなければ `due_at = created_at`。
NULLの待機期限は制約なし。1日を超える通常間隔では、上限によって通常間隔を短くしない。
例：Statusの成功後は15分、連続失敗後は30分→60分→120分。Blogは60分→120分→240分→480分。
判定時刻が実行可能時刻と等しくなれば対象とする。実際の開始にはジョブ起動周期・処理時間が加わる。
停止期間があっても1回だけ収集し、過去の予定枠を作ったり、埋め合わせたと報告したりしない。

- 間隔変更は次の判定から現在値で再計算する。短縮して期限を過ぎれば次のジョブで1回取得する。
- 自動収集を無効化しても、開始確定済みのHTTP取得・保存・分類は完了させる。再有効化時は履歴から判定する。
- 手動の `news collect --source ...` は通常間隔・失敗時の間隔・自動収集無効を省略できる。
  ソースの無効状態、承認済み登録、実行中の排他、配信元の待機期限は手動にも適用する。
  直前の取得がすでに完了していれば、手動の明示要求は別の取得になり得る。排他は同時実行を防ぐものとする。
- MarketHubで新しい収集経路を有効にする前に、承認済み各ソースへ無効のスケジュール行を作る。
  自動処理は行のないソースを見送り、新しい手動処理も設定不足を報告する。

## 二重起動と保存

既存の `uq_news_fetch_active_source` と[BeginFetch](fetch.go)を利用する。
事前の対象一覧は実行予約ではない。各ソースを開始する短いトランザクションの中で再判定する。

1. ソース行→スケジュール行→関連取得行の順にロックし、登録・有効状態・履歴・待機期限を再確認する。
   手動／自動開始、待機期限を伴う失敗記録、設定更新は同じ順序に揃える。
2. 期限を迎え、実行中の試行もなければ、同じトランザクションで `BeginFetch` を呼ぶ。
   競合・ロック待ちタイムアウトはその回を見送り、HTTPを送らない。既存の低水準APIは削除しない。
3. 開始Commitが成功したことを確認してからHTTPを送る。応答不明ならIDを再読取りし、確定できなければ停止する。
4. HTTPはトランザクション外で行い、既存の応答サイズ上限とタイムアウトを維持する。
5. 成功は既存の完了Txへ保存する。失敗は `FailFetch` と待機期限の延長を同じTxで確定する。
   完了・失敗Commitの応答不明はIDと保存内容で照合し、HTTPの再送や待機期限の短縮を行わない。

履歴確認には現在の確定状態を読むlocking readを使い、古いトランザクションのsnapshotだけで判定しない。
ロックはCommit／Rollbackで解放する。[MySQL 8.4のlocking read仕様](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)
に従い、HTTP中にDBの行ロックを保持しない。

強制終了で残った `running` は既存契約どおり自動奪取しない。所有プロセス・終了状態を運用者が確認し、
明示的に失敗を記録してから再開する。他ソースは継続できる。設定変更だけではこの状態を解除しない。

## 失敗・分類・鮮度

| 状態 | 次の扱い |
| --- | --- |
| 200応答、内容変更なし／0記事 | 正常に解析・保存できれば取得成功。既存の版を再利用し観測runを記録。通常間隔へ戻る |
| 通信・解析失敗 | 取得失敗を記録し上記backoff。前回成功した入力は保持。同一ジョブ内では再試行しない |
| 429／503と有効な `Retry-After` | 秒数またはHTTP日時をUTCの期限へ変換・保存し、backoffとの遅い方まで待つ |
| 不正な `Retry-After` | 時刻として採用せず、解析不可を報告して通常の失敗backoff。生ヘッダーは保存・ログ出力しない |
| DB障害・開始／終了の確定不明 | 成功と扱わず報告。保存された状態を照合してから再開。ローカルメモリだけで次回を予約しない |
| 取得成功・分類失敗 | 取得成功と分類失敗を分ける。取得のbackoffには数えず、APIは既存の完了ペアと分類状態を返す |
| ジョブ停止・長期間未実行 | 最終成功時刻から遅延を表示する。新記事0件／市場の変化なしとは解釈しない |

`Retry-After` の秒数はレスポンス受信時点から計算する。正しい期限がbackoff上限より遠い場合も短縮しない。
形式と意味は[RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after)に従う。
collectorはHTTP状態・受信時刻・解析済み待機期限と解析結果を構造化して保存処理と運用記録へ渡す。

分類の失敗は別の復旧対象。初期版は同じrunを毎分再分類する処理を追加せず、次の通常収集では新runを分類する。
同じrunの再分類は既存の保存データを使う運用対応とし、分類のためだけに再取得しない。
Sui BlogのMainnet対象0件の意味や分類条件は、このスケジュール変更で変えない。
収集・分類の状態と、最終確認／成功時刻、記事の公開時刻は別々に扱う。

## 実装・導入の順序

1. この追加DDL、間隔の範囲、失敗時の計算、手動取得の待機期限共有をレビューする。
2. storageへ追加DDLを返すAPIと設定保存・履歴参照・待機期限更新を実装する。接続・Tx・時刻は呼出側が渡す。
   既存 `Schema()` と当初DDLは保持し、追加DDLのAPI（例：`ScheduleSchema()`）を用意する。
3. MarketHubへ加算マイグレーション、共通の開始判定、単発の `collect-due`、設定変更用の管理コマンドを実装する。
   現行の登録承認・Mainnet分類・API snapshot・manifestの契約を維持する。
4. storage公開と本体の依存固定後、レビュー済みマイグレーションを適用する。初期行は無効で登録する。
5. 手動で期限判定と取得・分類を確認後、自動収集を有効化し、本番の定期起動を別途設定する。

停止は自動収集無効化と定期起動停止で行い、取得履歴や記事を削除しない。
既存の `003_news`、旧contentテーブル、過去のmanifestは変更しない。
Consoleの設定UI・公開APIへの追加項目・配信内容に応じた自動間隔調整・ETag／304対応は初期実装に含めない。
既存APIの最終成功時刻等は利用できるが、収集間隔の公開表示には別途API設計が必要。

## 実装時の受入条件

| ケース | 確認する結果 |
| --- | --- |
| 間隔59秒／60秒／604,800秒／604,801秒、版競合 | 範囲外・古い設定更新を拒否。待機期限は設定変更で消えない |
| 未収集、期限直前／同時刻、間隔短縮・延長、無効／再有効化 | 指定条件でのみ開始し、再起動後も同じ履歴から同じ判定になる |
| 自動2プロセス／手動と自動の競合 | 同じソースの実行中取得は1つ。自動側は完了後も期限を再判定し、同じ期限に重ねて取得しない |
| 3回以上の失敗、成功、通常間隔が1日超 | 2倍→4倍→8倍と上限・下限が成立。成功で通常間隔へ戻る |
| Retry-Afterの秒数／日時／不正値／設定変更／再起動 | 有効な待機期限を短縮せず、無効値から日時を捏造しない |
| 開始後の強制終了、Commit応答不明、失敗Txの障害 | 古い成功結果を保持し、不明な状態でHTTPを重ねない |
| 取得成功・分類失敗／対象0件、更新なし | 取得失敗・分類失敗・正常な空結果を混同しない |
| 長期停止、他ソースの失敗、過去snapshot再読取り | 追いつき連打なし。他ソースが進み、過去の入力とhashが不変 |

実装後、差分・リンク・DDL一致、単体テスト、vet、影響範囲buildと回帰を確認した。
使い捨てloopback MySQL 8.4.13ではDDL、CAS・期限保持、locking read、失敗Tx rollbackと、
MarketHubの手動／自動排他・HTTP中のTx外実行・待機期限・旧snapshot回帰を確認した。
本体MySQLテストはrace付きで成功し、storageも通常のMySQL全7件と非DB全race/vetが成功した。
最後に追加した同時設定CASのDB再確認はtool中断により結果未取得で、合格証拠に含めない。
テスト専用コンテナは削除済み。本番DB、実ニュースの取得、定期起動登録は行っていない。
